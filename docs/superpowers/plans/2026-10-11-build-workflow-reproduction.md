# From the accepted prototype to a reproducible build workflow

11 October 2026. Planning authorized by the author's
["okay then let us proceed"](../../history/2026-10-11-build-workflow-planning.md),
following the story and phone approvals of `fd03055`. This is a prospective
plan, not an executed protocol, a paid-run allowance or a skill change.
It follows the [stage review](2026-10-11-stage-review.md) and
[visual recovery plan](2026-10-11-visual-quality-recovery.md).

## Decision

First prepare one fresh **unchanged-skill baseline**. Ask whether an agent
can realize the approved story's explanatory relationships and evidence
boundaries in a convincing object-led prototype without seeing the accepted
implementation. Only a precisely attributed failure can justify new
instructions, followed by a matched rerun.

Keep all five meaning-level beats: question, scheduling, bench relationship,
evidence provenance and sample scope. The author explicitly requested the
depth added beyond the first three-beat prototype. Test one appearance as a
bounded diagnostic, not three appearances or the whole six-stop journey.
The actor may choose a different composition and visual language. The target
is explanatory quality, not a copy of the accepted apparatus.

This is **not completion of stop 4**: that stop includes implemented look
alternatives and a person's choice. Nor does this diagnostic exercise the
stop-5 three-whole-beat wording choices or the stop-6 complete-site checklist.
Do not redefine those requirements to fit a cheaper test.

## Why a new baseline, rather than new instructions now

The [process review](../../../evals/runs/codex-visual-quality-review-1/process-review.md)
separates these causes:

| Observation | Action before drawing a skill conclusion |
|---|---|
| Promised artifact-bearing faces and a connected explanation became uniform labels and disconnected pairs | Test whether the approved meaning survives implementation. A fresh miss can support a narrow build instruction. |
| Five of seven beats were table variants | Assess actual transformations and composition. The table-heavy storyboard partly prescribed this outcome, so attribution is not solely to the actor. |
| Six rows, restrained camera and static phone were coordinator choices | Remove those constraints in a new derivative fixture. Following them was not actor disobedience. |
| Review accepted readable lists and a visible canvas | Add explicit visual assessment, movement evidence and a real author gate. Test counts do not repair this measurement problem. |
| Wide faces distorted; the manual prototype needed a shared controls provider and connector/printing fixes | Separate engineering regressions from behavioral instruction experiments. Do not turn a local implementation repair into mandatory prose. |
| A text judge lacked pixels and the completion packet exceeded its input limit | Fix or bound evidence delivery prospectively. Neither issue is a portfolio actor failure. |

The approved prototype is a manual development result, not a saved baseline
agent that read an improved skill. The earlier row-card run and a corrected
non-sheet fixture cannot establish the causal effect of an instruction.
No candidate text is drafted into `skills/storyfolio/` by this plan.

The loop is teaching material. A diagram must not imply the 72-hour run
establishes two-year endurance. Do not invent current values, reporting
intervals, capacity, field use, pass/fail counts, or a radio-awake debugging
success. The confirmed derivative explicitly omits that incident account.

Evaluator-only material includes the accepted source, screenshots, exact
copy, geometry, poses and styles; recovery specifications containing that
solution; the earlier actor outputs and rejection analysis; this protocol;
and the judging rubric. Do not put them in the actor fixture. Reviewers may
use the accepted prototype as a quality reference, not a pixel-match target.
Supplying the non-sheet premise and approved narrative tests realization,
not independent concept discovery or profile-to-story planning.

Configuration isolation is not a filesystem read jail. Use a fresh external
workspace and the existing restricted capability profile, disclose only
fixture paths, and audit saved commands/output for cross-run or repository
reads. A discovered read of held-out solution material invalidates an
independent-reproduction claim; missing read telemetry remains a limitation.

## Local preparation before any paid call

These are implementation tasks for the next approved preparation step, not
completed work. Keep new tooling separate from frozen historical copies.

1. **Represent the diagnostic honestly.** The current
   [case validator](../../../evals/lib/build.mjs) accepts only stops 4, 5 and 6;
   [criterion eligibility](../../../evals/lib/build-score.mjs) keys off those
   stops. Add a versioned `prototype-depth` task kind with its own observation
   mapping, never a fake `requestedStops: [4]`. Preserve old case semantics.
   Test schema rejection, frozen task identity, turn limits, incomplete
   attempts, criterion eligibility, no overwrite and no automatic retry.
   Build-start preflight can be observed; before-stop-1 timing cannot.
2. **Freeze the derivative and neutral expectations.** Write and review its
   fact sheet, fictional confirmations, asset provenance, storyboard and
   allowlist. Freeze ordered beat IDs and required evidence distinctions
   independently of actor code. Permit newly authored headings/copy while
   checking heading structure and factual meaning, instead of importing the
   accepted prototype's exact sentences into string matchers. Version any
   checker extension and retain all existing strict fixture tests.
3. **Separate known engineering risks.** Reproduce relevant face-aspect and
   scene-controls issues in deterministic minimal cases before paying an
   actor to encounter them. The controls-provider adaptation is documented
   [here](../../../prototypes/fixture-study/content/object-design.md).
   If a shared fix is needed, make it a separately reviewed engineering
   change with tests before freezing the common engine for both arms. Do
   not silently copy prototype code or change the engine only in a candidate
   arm and call the outcome a skill-only improvement. No shared fix is
   authorized or applied by this planning checkpoint.
4. **Prepare independent visual measurement.** Reuse coordinator-owned build,
   type, lint and browser checks, adding the missing short viewport and
   actual forward/reverse transition sampling. The current
   [checker scope](../../../evals/builds/acceptance.md) covers six modes and
   settled positions, not this complete visual question. Adapt capture code
   outside frozen studies. Derive sampling from frozen beat expectations and
   measured geometry, not candidate formations or candidate test results.
   Test missing beats, wrong control targets, reversed/absent motion samples,
   reduced-motion stillness and all post-context-loss beat captures.
5. **Calibrate without a model run.** In new retained calibration artifacts,
   apply the visual criteria to existing accepted and rejected originals.
   Record where each criterion distinguishes them and which comparisons are
   unobserved because scenes differ. Do not rerun the five-beat numeric
   contract against the old seven-beat site and call missing IDs a creative
   failure. This is a sanity check using known examples, not blind validation
   or evidence of general scoring accuracy. Test automation separately with
   small known-good and known-bad fixtures. Do not tune criteria after the
   new baseline is seen.
6. **Preflight judge delivery.** Keep the first judge behavioral/text-only;
   do not imply it sees pixels. Test representative complete source/tool/
   acceptance packets and synthetic boundary cases against both current
   guards: 2 MiB UTF-8 and 1,048,576 UTF-16 code units. The
   [completion diagnosis](../../../evals/runs/codex-build-completion-1/embedded-completion-1/baseline-1/audits/judge-packet-size.md)
   rules out simple minification as a repair for that old packet. If complete
   delivery cannot fit, stop preparation for a separately scoped transport
   decision. A paged read-only accessor is a proposal, not an available tool.
   Never truncate failed commands, source or reports, infer unread evidence
   from paths, or spend a judge attempt to discover a known size failure.
7. **Freeze and prove the exact environment.** Commit case, prompt, rubric,
   task mapping, engine, lockfile, checker, capture and judge implementations.
   Record CLI and capability configuration, disabled skills and pre-scaffold
   inventory. Use the runbook's no-model `--dry` and `--prepare` paths only
   after the new task kind is supported. Prove loopback access, blocked
   external requests, production build and browser use in that actual actor
   workspace. Preserve setup and failure evidence in the new repository
   cohort. This probe is not the actor's own preflight. Do not relax to
   unrestricted network or an unsandboxed actor to make it pass.

The existing command interfaces are in the [runbook](../../../evals/README.md#bounded-build-baseline).
New-case paid commands are intentionally not presented as executable today:
the case and diagnostic support do not yet exist. The preparation handoff
must supply exact validated commands, input digest, outstanding limitations
and the cost decision before launch.

## Prospective assessment

Keep four results separate: technical checks, independent behavioral
judgement, source-bound visual review, and the author's actual assessment.

| Visual question | Required observation, not an implementation prescription |
|---|---|
| Backdrop | The object explains a work relationship or presents useful evidence; a canvas containing only repeated headings does not suffice |
| Depth | All five beats contribute their distinct meaning and lead to a supported closing answer; section count alone is not depth |
| Swap | The object and behavior are specific to this work, not the same generic scene with nouns changed |
| Detail and hierarchy | Important artifacts can be inspected; surface detail supports meaning and does not crowd reading or controls |
| Spatial quality | The same recognizable object changes meaningfully across the story; composition, movement and occlusion serve that explanation |
| Phone and still modes | The narrow viewport retains a meaningful visual treatment; reduced-motion and failure modes preserve complete accessible explanations |

Factual ownership, provenance and evidence boundaries are mandatory in every
mode. Accessible HTML may repeat scene information; do not hide it to pass
Backdrop. Do not count effects, prescribe fixed printing everywhere, demand
four pieces, force one color palette, or require every possible engine hook.

Capture the candidate's five rests and all four travel intervals in both
directions. Include desktop 1440 by 900, phone 390 by 844, short 1280 by 720,
reduced motion, no WebGL, no JavaScript and actual context loss. Exercise
every implemented interactive control by pointer and keyboard; do not force
the accepted prototype's exact controls on a different design. Preserve
source hashes, full originals, actual positions, failures and conditions.
Review originals, not just contact sheets; sampled motion is not an
every-frame or frame-rate guarantee.

The text judge assesses supported claims, attribution, implementation of
the brief, preflight, scope, documentation and honest reporting. Pixel
quality remains unobserved to that judge. Missing image-view events in CLI
JSON do not establish skipped image review, as the
[first baseline correction](../../../evals/runs/codex-build-1/findings.md#independent-judgement-and-reviewed-corrections)
already demonstrated. Coordinator visual review and real author review
must be saved separately. Approval of `fd03055` does not approve new output
or supply its physical-phone check.

Record each criterion as pass, fail or unobserved, plus artifact completeness
and environment/transport status. No average score may hide a missing beat,
unsupported claim or rejected visual result. A deadline-limited partial
artifact is incomplete evidence, not automatically an instruction defect.

## Proposed paid envelope, not authorized yet

- One fictional case, one fresh unchanged-skill baseline, one actor turn.
- Established project roles: `gpt-6.1-sol` actor, medium reasoning, with a
  15-minute process deadline and the runner's two-second force-kill grace.
  No continuation, automatic retry or corrective follow-up.
- At most one fresh `gpt-6-astra` medium behavioral judgement, ten-minute
  deadline, only if the actual post-run complete evidence packet passes
  unpaid transport validation. An oversize packet is preserved and leaves
  judgement unobserved, without an improvised reduced brief or new call.
- All five beats are the target, not a guarantee within that time. One
  appearance narrows this to feasibility and quality diagnostics. An
  incomplete prototype may still receive that one behavioral judgement if
  its preserved evidence packet is complete and passes validation. Missing
  or corrupt evidence blocks judging. In either case, record incompleteness
  and usage; no further actor turn is allowed without a new decision.
- No candidate rerun, second baseline, full-journey cohort, early-stage
  experiment or planning regression is included in this allowance.

These bound model-call count and process time, not token consumption or
dollars. Existing `maxTokens` and `maxUncachedTokens` only gate later turns;
with one permitted turn they provide no in-flight spending cap. If the
legacy `maxTokens` field is retained, record its value and this limitation,
not a supposed token budget. A hard provider-side spending cap would need a
separate supported mechanism and decision, not an invented CLI setting.

For historical context only, the [first baseline](../../../evals/runs/codex-build-1/findings.md#protocol-provenance-and-usage)
actor took 802.071 seconds and reported 4,603,905 input tokens, including
4,470,144 cached, plus 25,845 output. The judge took 112.016 seconds with
267,133 input and 4,390 output. Combined uncached input plus output was
431,129. This is an observed older case, not a forecast for this five-beat
task or a dollar estimate. Preserve raw usage and report cached, uncached
and output counters separately; resumed counters from other studies must
not be treated as distinct billed usage.

## What follows the baseline

1. Audit the actual evidence and assign each miss to actor behavior, source
   ambiguity, fixture constraint, engine, environment or measurement.
2. If it passes, do not add redundant skill prose. Preserve the result and
   plan the next uncovered workflow gate. One case is not a success rate.
3. If a behavioral miss remains, propose the smallest instruction, linking
   its exact saved run and evidence. Obtain a separate rerun decision. Hold
   fixture, prompt, engine, models, rubric and capture method fixed across
   that candidate comparison. A necessary change to those inputs starts a
   newly labelled baseline rather than a causal before/after claim.
4. A supported build entry point still requires scope/activation evidence.
   Before-stop-1 preflight, three concept sketches, implemented look choices,
   three whole-beat wording versions, relevant optional-skill recommendation
   and refusal handling, planning-only regression and a non-sheet full
   journey retain their own questions and cost gates. The approved prototype
   is not a substitute for the whole-site proof.
5. Packaging follows demonstrated capability and the remaining Stage 1
   dispositions. No README build promise, release or push follows from this
   planning checkpoint.
